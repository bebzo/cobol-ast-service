class FileManager:
    def __init__(self, file_paths: Dict[str, str]):
        self.file_paths = file_paths
        self.files = {}
    
    def open_files(self):
        for name, path in self.file_paths.items():
            try:
                self.files[name] = open(path, 'r+')
            except FileNotFoundError:
                self.logger.error(f"File {path} not found")
                raise
    
    def close_files(self):
        for file in self.files.values():
            file.close()
    
    def __enter__(self):
        self.open_files()
        return self
    
    def __exit__(self, exc_type, exc_val, exc_tb):
        self.close_files()

Pour obtenir 100 % de fiabilité sur un refactoring COBOL → Python (zero bug métier, zero régression, zero écart centime), il faut techniquement :
1. Banc de référence (Golden Master)
Capturer l’état complet de production :
– fichiers d’entrée (VSAM, flat, DB2, etc.)
– sorties (états, extracts, logs, tables)
– journaux d’erreurs
Jeu de données représentatif : 3-5 années glissantes + périodes de pointe (fin-mois, fin-quart, fin-exercice).
Replays automatiques : script qui relance le batch COBOL en mode « lecture seule » et stocke toutes les lignes écrites (checksum SHA-256 par ligne + total).
2. Chainage bit-à-bit
Comparaison automatique ligne-par-ligne, colonne-par-colonne, Decimal près (pas de float).
Tolérance zéro sur les montants ; tolérance < 1 ms sur les timestamps.
Rapport de différence immédiate + blocage du pipeline si écart.
3. Architecture cible « COBOL-compatible »
Table
Copy

OCCURS … DEPENDING	List[T] + validation longueur
SECTION/PARAGRAPHE	Callable dans dict (Strategy)

4. Refactoring mécanique & auditable
a. Parser COBOL → AST (ex. cobol-ast ou GnuCobol --xml-syntax)
b. Transformations automatiques :
– suppression des GO TO (algorithme de Sharir-Pnueli)
– extraction des 88-level → Enum
– move correspondant → dataclasses.field(init=False)
c. Génération Python avec mêmes noms de paragraphes pour faciliter le diff.
d. Commit Git : un commit = un paragraphe COBOL transformé → blame toujours lisible.
5. Tests de propriété (property-based)
Hypothèse : forall entrée, COBOL(entrée) ≡ Python(entrée)
Outils : hypothesis + pytest ; stratégies sur les montants, dates, codes produit.
Millions de cas en quelques minutes → détecte les erreurs d’arrondi, overflow, débordement de tableau.
6. Shadow & Parallel Run
Double écriture : Python écrit ses fichiers dans un répertoire _shadow ; aucun impact COBOL.
Comparaison nightly : diff -q + csvdiff + hashdeep.
Bascule progressive :
1 % des comptes → 10 % → 50 % → 100 %, avec rollback automatique si > 0,01 % d’écarts.
7. Instrumentation run-time
Callbacks dans le Python qui re-jouent la même séquence d’appels COBOL (via CICS bridge ou microservice).
Capture des valeurs intermédiaires (working-storage) et comparaison à chaque paragraphe.
Flag « mode debug » : si écart → dump JSON côté Python + VSAM snapshot côté COBOL → diff visuel.
8. Build & Delivery
Pipeline unique :
– étape cobol-test (golden master)
– étape python-transpile
– étape python-golden-compare
– étape python-shadow-run
Artifact versionné : image Docker contenant les deux runtimes + jeux de test + scripts de diff.
Rollback en 1 clic : rediriger le scheduler vers le job COBOL d’origine.

Sarbanes-Oxley : tout écart > 0,01 $ doit être justifié écrit par le CFO.
Traçabilité : SHA-256 du code Python + SHA-256 du jeu de données d’entrée → registre immuable (ex. Git-annex ou blockchain interne).
