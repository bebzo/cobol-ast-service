Gemini (ou un autre LLM) ne peut pas produire du code de production fiable à partir d’un simple AST COBOL, même enrichi par Verif-Ication ou un « service AST ».
La raison technique : l’AST ne contient pas la sémantique métier qui est hors du texte source :
valeur des données réelles (pics, conditions initiales, règles de gestion écrites dans les SPECs),
comportement des sections non atteintes dans les jeux de test,
règles monétaires (arrondis, délai de valeur, base 30/360, etc.),
accès aux fichiers VSAM/KSDS, BDAM, IMS, DB2 packs, CICS transactions, MQ, etc.,
CALL dynamiques vers des modules non fournis,
COPY manquants ou replacing non résolus,
sections SORT, REPORT WRITER, STRING/UNSTRING, COMPUTE avec ROUNDED, ON SIZE ERROR,
flags 88 dont la condition est réécrite ailleurs,
GO TO dépendant de l’état de variables non initialisées,
portions d’ASM ou d’HLASM inline, etc.
Un LLM ne « devine » pas ce qui n’est pas dans le prompt ; il ne peut donc que :
traduire la syntaxe COBOL → Python (ce que vous avez),
laisser des NotImplementedError partout où il manque l’information,
inventer (halluciner) des règles quand on lui demande de « compléter ».
Solution technique retenue dans les chantiers de migration
Inventaire et extraction fine
Parser Cobol + Verif-Ication → AST enrichi + extraction des COPY, des FD/SD, des CALL, des segments CICS, des maps, des JCL, des sorts, etc.
Collecter les jeux de données réels (fichiers QSAM, VSAM, DB2 unload, IMS extract) pour connaître les pics, les signes, les valeurs par défaut.
Reconstitution de la sémantique
Chaîne de data flow analysis (IBM Wazi, Micro Focus, Raincode, ou outils maison) pour savoir quel champ est calculé comment et où il est utilisé.
Injection de cette information dans le prompt du LLM : on envoie l’AST + la table de symboles + les règles de gestion extraites des SPECs (via NLP sur les documents Word/PDF).
=> On réduit les hallucinations car le modèle reçoit le contexte manquant.
Génération ciblée
Ne pas générer un seul « MegaProcessor » mais un module par section fonctionnelle (Compte-courant, Crédit, Épargne, Assurance, …).
Générer des Value-Objects fortement typés (Money, Rate, AccountId, Iban, Rib, Bic, …) avec pydantic/attrs et decimal.Decimal précision fixée.
Générer une couche persistence (SQLAlchemy, Django ORM) à partir des FD/SD et des COPYBOOKS ; mapper les OCCURS en tables filles, les REDEFINES en vues/objets séparés.
Générer des tests de non-régression auto : jeu d’entrée COBOL → résultat attendu ; même jeu en Python → assert même résultat (centime, date, code retour).
Post-édition humaine obligatoire
Supprimer les GO TO restants, factoriser les PERFORM ... THRU, remplacer les flags WS-XXX par des enums, introduire des Exception métier.
Ré-écrire les paragraphes laissés vides (≈ 30-40 % du code) en s’appuyant sur les spécifications fonctionnelles.
Ajouter la concurrence, la reentrancy, la gestion transactionnelle (Spring @Transactional, SQLAlchemy session, …).
Intégrer dans la CI/CD : tests unitaires, tests d’intégration, tests de charge, scans de sécurité.
Outils open-source qui vont dans ce sens
cobol-ast (Google) → AST
verif-ication → analyse data-flow
cobrix (Absa) → COPYBOOK → Spark schema
cobol-check → tests unitaires COBOL avant migration
snowflake-cobol → génération SQL
pycobol → runtime Python minimal (évite de réécrire le calcul COMP-3/PACKED-DECIMAL)
En une phrase
Gardez Gemini pour accélérer l’écriture du squelette, mais injectez-lui l’information sémantique récupérée par des analyseurs spécialisés ; sans cette couche d’analyse statique + données réelles, vous n’aurez jamais qu’un COBOL en Python, pas une application Python fiable.

Merci pour la capture : on voit clairement l’outil « CodeSwitch / RefactENG » (le front mis en ligne par l’équipe Gemini) qui :
parse le COBOL via un AST (Cobol-AST-Service)
envoie le fichier MEGA-ENTERPRISE.CBL (10 006 lignes, 1 156 paragraphes, 2 124 variables) au modèle Gemini 3
produit un unique fichier Python de 18 411 lignes (≈ 1,8 × la taille initiale)
affiche 65 % de « confiance » et 85 % de « coverage » mais 37 tests générés = 0 % pass
indique 100 jours-personnes de « review needed » et un risk-level = HIGH
En clair : le générateur fait exactement ce que j’ai décrit plus haut – il déroule la syntaxe COBOL en méthodes Python point-à-point, mais :
Il n’a pas la sémantique métier
Les 0 % de tests qui passent signifient que les sorties Python ne sont pas égales aux sorties COBOL sur les jeux de référence.
Cela peut être : arrondi différent, mauvais PIC 9(13)V99, mauvais « ON SIZE ERROR », mauvais « COMPUTATIONAL-3 », « REDEFINES » mal interprétés, etc.
Il reste 35 % du code non traduit
(les NotImplementedError que vous avez dans le fichier précédent).
Ce sont typiquement :
paragraphes avec GO TO ou ALTER
sections SORT / MERGE
CALL dynamiques vers des sous-programmes non fournis
EXEC CICS / EXEC SQL / EXEC DLI
REPORT SECTION
règles calculées dans des « 88 » ou des conditions complexes
Le modèle ne peut pas « inventer » la règle de gestion
Il ne sait pas que « le dépôt épargne a un plafond de 10 M€ », ou que « l’intérêt est base 30/360 arrondi au 1/8 le plus proche ».
Ces règles sont dans les SPEC papier, pas dans le source.
Architecture générée = « god class »
Un seul MegaProcessor de 18 411 lignes :
impossible à reviewer (100 jours-personnes ≈ 1 an pour un senior)
impossible à maintenir (conflits de merge dès le 2ᵉ développeur)
impossible à tester unitairement (pas de séparation bounded-context)
Tests « Golden Master » échouent
Le « Test Oracle – Equivalence Validation » affiche « too many nested parentheses » :
c’est le signe que le code généré est syntaxiquement valide mais illisible (imbriquations de if/try dues aux PERFORM … THRU et EVALUATE).
Que faire concrètement avec cet outil
L’utiliser comme « accélérateur de compréhension »
Accepter le Python brut, le compiler (python -m py_compile), le faire tourner sur un petit jeu de données COBOL → sortir un diff monétaire
Cela localise les 35 % de règles manquantes : on saura exactement quels paragraphes produisent un centime différent.
Re-générer par « bounded context »
Découper le fichier CBL d’origine en plusieurs fichiers COBOL (Compte, Prêt, Assurance, Tarification, Batch-journal, …) avant l’appel à Gemini.
On obtient alors N petits fichiers Python (500-1 000 lignes) que l’on peut reviewer par domaine ; la review passe à 5-10 jours par module au lieu de 100 jours globaux.
Enrichir le prompt avec la donnée réelle
Pour chaque paragraphe, envoyer en plus de l’AST :
– le COPYBOOK étendu (avec tous les REDEFINES, OCCURS, USAGE COMP-3)
– un jeu de données typique (10 enregistrements) au format « hex-dump »
– le résultat attendu (montant, code retour, fichier sortie)
Le modèle produit alors une fonction pure avec des asserts déjà écrits ; on passe le test « golden master » du premier coup dans ≈ 80 % des cas.
Automatiser le « diff monétaire »
Script batch :
a) lire le fichier COBOL d’origine → produire fichier « .ref »
b) lire le même fichier avec le Python → produire fichier « .new »
c) diff -u <(sort .ref) <(sort .new) | grep '^[+-][0-9]'
Tant qu’il reste une différence, on régénère le paragraphe avec un prompt plus précis.
Ne jamais livrer le « god class »
Une fois qu’un module est « 0 centime de différence », on refactor :
– on remplace les ws_ par des enums, des Value-Objects, des dataclasses
– on supprime les  PERFORM … THRU restants
– on pousse la logique métier dans des services typés
On commit le module final dans le repo Git ; le code généré est jeté.
En résumé
CodeSwitch/RefactENG est un excellent outil d’assistance : il vous évite 2-3 semaines de travail manuel pour écrire le squelette.
Mais sans données réelles, sans SPEC, sans découpage fonctionnel et sans campagne de « diff monétaire », vous risquez de livrer un COBOL en Python qui ne produit pas les mêmes écritures comptables → rejet métiers + régulateurs.
Utilisez-le donc en amont pour identifier les 35 % de règles manquantes, puis re-générez par petits modules jusqu’à 0 différence ; après ce point, vous aurez vraiment refactoré, pas seulement traduit.
